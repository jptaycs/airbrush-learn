# CLAUDE.md

Guidance for Claude Code (or any AI agent) working in this repo.

## What this project is

A plain static site for **Airbrush Learn** (airbrush.gallery) — an SEO blog about airbrushing (buying guides, techniques, comparisons, maintenance), owned by SprayGunner. It replaces a previous WordPress setup. No CMS, no server-side runtime — every deploy is a static build that auto-publishes on git push (Netlify).

Article content itself is **not written here**. It's produced by a separate n8n multi-agent pipeline, which — as its last step — commits the finished article and its hero image directly into this repo via the GitHub Contents API. This repo only turns whatever's already committed into pages; it never fetches anything from n8n itself.

## Commands

```bash
npm install
npm run dev      # astro dev — reads whatever's already in src/data/articles.json
npm run build    # astro build -> dist/
```

There is no test suite. There is no lint step configured yet.

## How a build actually works (read this before changing the pipeline)

1. n8n's content pipeline generates an article, then — as its last two steps — commits `src/data/articles.json` (with the new article merged in) and `public/images/<slug>.png` (the hero image) straight to this repo's `main` branch via the GitHub API.
2. That commit triggers Netlify's normal git-push auto-deploy. There is no prebuild fetch step and no build-time network dependency on n8n — by the time a build runs, the content is already sitting in the repo.
3. Astro builds normally. `src/pages/index.astro` and `src/pages/posts/[slug].astro` both `import articles from '../data/articles.json'` — they never fetch anything themselves.

**Why it's built this way:** committing content directly means a build never depends on a live external service being reachable — if n8n or its webhook is down, existing content still builds and deploys fine. It also means every article change has full git history and is trivially revertible (`git revert`) if something publishes wrong.

`src/data/articles.json` is a normal tracked file, not generated at build time — n8n's commits are the only thing that update it in production. Don't manually edit it and expect it to survive the next n8n run without conflict; treat n8n as its source of truth going forward.

## Data contract

Each article object in `src/data/articles.json` has these fields:

| field | used for |
|---|---|
| `slug` | URL path (`/posts/<slug>`) and image filename (`/images/<slug>.png`) |
| `title` | `<title>`, `<h1>`, OG/Twitter meta, card heading |
| `excerpt` | meta description, OG description, card blurb |
| `content_html` | article body — inserted via `set:html` in `[slug].astro`. **This is the field the templates actually render.** |
| `image_prompt` | the prompt used to generate the hero image; carried through for reference, not rendered anywhere |
| `source_topic` | the target SEO keyword from the content brief; carried through for reference, not rendered anywhere |
| `published_date` | sort order (newest first) and displayed date. Format is `YYYY-MM-DD` (n8n-generated entries) or `YYYY-MM-DDTHH:mm` (admin's edit form uses a `datetime-local` input, so a manual edit can add a time) — both sort correctly as plain strings. The public site (`src/lib/formatDate.js`'s `displayDate()`) always renders date-only regardless of which format is stored; only `/admin`'s own article table and edit form show the time when present. |
| `category` | category badge, `/category/<slug>` archive-page membership, mega-menu counts — one of 10 fixed slugs (see `src/data/categories.js`); missing/unrecognized values are treated as uncategorized |
| `status` | `"draft"` or `"published"`. A missing/absent field is treated as `"published"` — no migration was needed when this field was introduced. Drafts are filtered out of the homepage, category pages, and the sitemap, but still get a `noindex`'d `/posts/<slug>` page so they're directly previewable. See `/admin` below. |

The n8n workflow's `Publish Guard (block fallback)` node is what decides whether an article reaches the commit step at all; nothing here re-checks that. The n8n workflow does **not** currently set `status: "draft"` on new entries (see To Do below) — until it does, every article it commits is immediately live, same as before `status` existed.

If you add a new field, update it in two places: the n8n workflow's "Build Article Entry" node (where the JSON object is constructed) and wherever it should be consumed in `src/pages/`.

### `src/data/gallery.json`

Unlike articles, gallery pieces come from two sources now: curated entries committed directly (as before), and community submissions approved via `/admin`'s "Gallery Submissions" tab. Both produce the identical shape: `{ slug, title, category, image, credit }` — `category` is a `src/data/galleryCategories.js` slug (not `categories.js`), `image` is a bare filename resolved against `public/images/gallery/`, and `credit` is the submitter's name for approved submissions or the existing attribution string for curated pieces. There's no field distinguishing a piece's origin — once approved, a submission is indistinguishable from a curated entry.

### `src/data/topics.json`

The n8n content pipeline's topic queue and publish-status tracker — added 2026-08-18 to replace a Google Sheet that turned out to be structurally unreliable for this (see the `n8n-pipeline-architecture` memory file for the full history of why). This repo is now the source of truth for what topics exist and their status, managed via `/admin`'s "Topics" tab (`netlify/functions/topics-{list,save,delete}.js`, same GitHub-Contents-API pattern as the article/gallery admin functions) and by n8n itself, which is expected to call `topics-list` to find the next eligible topic and `topics-save` to report its outcome, instead of talking to Google Sheets directly. Each entry: `{ id, category, search_intent, article_title, target_keyword, priority, status, publish_date, notes }` — field names and `id` values were migrated 1:1 from the old sheet's `" #"` column so nothing was renumbered. `status` is free text, not a strict enum, but n8n's filtering logic expects exactly `"Not started"`, `"Published"`, or `"Blocked"` (case-sensitive) — same convention the sheet used. `category` is a free-text label (e.g. `"Buying Guides"`), not a `categories.js` slug — it's mapped to a slug later, inside the "Build Article Entry" node's `categoryMap`, same as before.

**As of 2026-08-18, n8n's workflow has not yet been updated to use this** — it still points at the old Google Sheet. Wiring it up means replacing `Get row(s) in sheet` with an HTTP Request node calling `topics-list` (with an `x-admin-password` header, same secret as everything else in `/admin`), and replacing `Update row in sheet` with an HTTP Request node calling `topics-save` with the topic's updated `status`/`publish_date`. The WordPress-posting branch (`Upload Featured Media to WordPress` → `Create WordPress Draft Post`) was intentionally left untouched during this migration — it's known dead weight (see Known gaps below) but wiring topics.json in didn't require touching it.

### `src/data/products.json`

A curated reference list of real SprayGunner products, unified 2026-08-21 from what was previously a separate `gearAdvisor.json` placeholder file (see the closed "Swap in real Gear Advisor data" To Do item below). It serves two consumers: the `/gear-advisor` quiz (`src/components/GearAdvisor.astro`, imported directly at build time) and the n8n content pipeline (via `netlify/functions/products-list.js`, a read-only endpoint), which prefers linking a specific product from this list over the generic `spraygunner.com` root. Each entry: `{ name, type, price, budgetTier, subjects, experience, blurb, url }`.

- `type` — one of `airbrush`, `compressor`, `kit`, `accessory`, or `paint`. Only the first four are reachable by the quiz's scoring logic in `GearAdvisor.astro` (`isAirbrushOrKit()` matches `airbrush`/`kit`, and separate filters match `compressor` and `accessory` directly); `paint` is a fifth value used only by the content pipeline for linking and is deliberately invisible to the quiz — it never appears in any of `scoreGear()`'s filters.
- `budgetTier` — `budget` (under $100), `mid` ($100–300), or `pro` ($300+). The $300 boundary is ambiguous by that description (it satisfies both "$100–300" and "$300+"); the convention used here is that an item priced at exactly $300 is tagged `pro`.
- `subjects` — an array of slugs from `src/data/galleryCategories.js` (**not** `categories.js`). Only set for `airbrush`/`kit` items; omitted entirely for `compressor`/`accessory`/`paint` items, which the quiz's scoring treats as suiting any subject.
- `url` — a real spraygunner.com product URL tagged `?utm_source=airbrushlearn&utm_medium=gear-advisor`. This URL is shared between the quiz and the (not-yet-live) content pipeline; it's currently tagged for the quiz since that's the only live consumer today — revisit the `utm_medium` attribution if/when the pipeline starts rendering these links in production.

This file is a curated snapshot sourced from spraygunner.com's live Shopify collection feeds, not a live sync — prices and availability may drift over time; see `docs/superpowers/specs/2026-08-21-spraygunner-product-reference-design.md` for the full sourcing process if it ever needs refreshing.

### Image regeneration (`/admin`)

Added 2026-08-23 (an earlier version of this same idea was designed and briefly implemented 2026-08-21, then deliberately shelved before shipping — this is a fresh build, not a recovery of that one, since nothing from it was ever committed). Lets an operator fix a single bad hero image without re-running n8n's whole pipeline: in an article's edit panel, "Regenerate Image" reveals the article's `image_prompt` in an editable textarea; "Generate" kicks off the actual work.

This is the **only** place in this repo (outside n8n itself) that calls an image-generation API directly — every other function only ever talks to GitHub or Netlify Blobs. Because generation can take well past a plain Netlify Function's ~10–26s timeout, the real work runs in `netlify/functions/image-regen-run-background.js`, a **background function** (`export const config = { background: true }` — Netlify discards its return value and always answers the triggering request with 202, regardless of what the handler does or returns). It writes progress to a `image-regen` Netlify Blobs store keyed by slug (`pending` → `done`/`error`), which `netlify/functions/image-regen-status.js` exposes for the admin UI to poll every 3s (giving up after ~2 minutes with a "may still finish in the background" message, since the job itself can run up to 15 minutes). On success it commits the new PNG to `public/images/<slug>.png` and updates just that article's `image_prompt` field in `articles.json` (a single-field write, retried once on a stale sha — deliberately narrower than `admin-save.js`'s full-article write, so it can't clobber an unrelated concurrent edit) — matching n8n's own `gpt-image-2`/high-quality model and a `1536x1024` size — confirmed 2026-08-25 by reading the live `SEO Content Creation - Multi-Agent Pipeline (v5- Jerome).json` export directly: its `Generate Featured Image` node uses the identical `model: 'gpt-image-2', quality: 'high', size: '1536x1024'`. Because a GitHub commit still needs a Netlify deploy to reach the live site, the `done` status also carries the raw generated image as base64 so the admin panel can preview it immediately rather than waiting on that deploy.

Requires a new `OPEN_AI_KEY` Netlify env var (see Deployment below) — separate from whatever credential n8n's own OpenAI node uses internally, since Netlify Functions can't reach into n8n's credential store. **Verified against a real end-to-end round trip 2026-08-24**, once `OPEN_AI_KEY` was added to `.env` (production Netlify env var still needs confirming separately, same as any other of this repo's env vars): ran `netlify-cli dev` locally and regenerated the draft article `airbrush-clogging-guide`'s hero image using its existing real `image_prompt` — `image-regen-run-background` returned 202, `image-regen-status` correctly progressed `pending` → `done` (~2 min), a real `gpt-image-2`/high-quality image was generated, and two real commits landed on `main` (`c80ef2c` image, `ad563e1` image_prompt field). Both were reverted afterward (`d3014dc`) since it was a verification run against a real article, not an actual bad-image fix — the image_prompt commit turned out to be a content no-op (same prompt text in, same text out) so only the image needed restoring. **Also discovered while doing this:** local `main` was 3 commits behind `origin/main` again (same class of drift as the 2026-08-23 "81 commits behind" incident) — synced via stash + `git pull --ff-only` + stash pop before touching anything, per that incident's established recovery pattern.

### Hero/gallery image WebP optimization (build-time)

Added 2026-09-03 to cut Netlify bandwidth-credit cost (bandwidth is billed at 20 credits/GB — see Deployment below). `scripts/generate-webp.mjs` runs before `astro build` (see the `[build].command` in `netlify.toml` and the `"build"` script in `package.json`) and generates a `.webp` sibling next to every hero image (`public/images/*.png`) and gallery image (`public/images/gallery/*.{jpg,jpeg,png}`) using `sharp`, skipping any file whose `.webp` is already newer than its source. `src/lib/optimizedImage.js`'s `webpSrcFor()` checks at render time whether a given image's `.webp` sibling actually exists on disk and, if so, the four render sites (`ArticleCard.astro`, `posts/[slug].astro`, `index.astro`'s featured card and gallery tiles, `GalleryGrid.astro`) wrap their `<img>` in a `<picture>` with a `<source type="image/webp">` pointing at it; if it doesn't exist, they render the plain `<img>` exactly as before. **The original `.png`/`.jpg` file stays canonical everywhere else** — OG/Twitter meta (`ArticleSchema.astro`, `BaseLayout.astro`'s `ogImage`), the `/images/<slug>.png` data-contract path, and everything n8n/`/admin`/`image-regen-*` commit — only the on-page `<img>` gets the smaller variant, and only when one was actually generated. Generated `.webp` files are gitignored (`.gitignore`); they're a build artifact regenerated on every deploy, never committed, so n8n's and `/admin`'s commits are unaffected.

This is deliberately fail-safe in both directions: the generator script never throws (every file is wrapped in its own try/catch, `sharp` itself is dynamically imported so a missing/broken install just skips optimization with a warning instead of failing `node scripts/generate-webp.mjs && astro build`), and a page never references a `.webp` that doesn't exist (the existence check happens at render time, not just assumed). Worst case for any bug here is a missing bandwidth optimization, never a broken image or a failed deploy.

**Verified locally 2026-09-03** (once Node.js turned out to be available after all — `C:\Program Files\nodejs`, just not on the session's PATH): `npm install` pulled in `sharp` cleanly, `npm run build` generated all 70 hero/gallery WebP files with 0 failures, and the size difference was far larger than estimated — **113.9MB of PNGs became 5.6MB of WebP, a 95% reduction** (individual heroes went from ~2.3-2.4MB to ~136-148KB). Confirmed in the actual `dist/` output: both `.png` and `.webp` present for every image, the four render sites' rendered HTML correctly emits `<picture><source type="image/webp" srcset="/images/<slug>.webp">` with the `.png` `<img>` fallback, and `ArticleSchema.astro`'s OG/Twitter/JSON-LD `image` fields still resolve to the original `.png` — the data contract held. Not yet checked in an actual browser (only the built HTML/file output was inspected) and not yet verified as part of a real Netlify build specifically (only local `npm run build`) — worth a quick look once builds are reactivated.

## Conventions

- **Styling is Tailwind CSS.** Design tokens (colors, spacing, radius, fonts) live in `tailwind.config.mjs`, mapped from the original brand values — change the palette there, not by hunting through components. `global.css` only holds the three `@tailwind` directives plus genuinely global element resets (`html`, `img`, `body` font smoothing, and a base `a`/`a:hover` rule for anchors — like n8n's raw `content_html` — that can't carry utility classes directly). Article body content (`content_html`, rendered via `set:html`) is styled through the `@tailwindcss/typography` plugin's `prose` classes, not hand-written CSS.
- **Client-side JS is scoped to one file.** `src/components/PageInteractions.astro` carries the site's only client-side script — a cursor spray-trail effect, scroll-reveal animations, and header/mega-menu polish, included once via `BaseLayout.astro`. It's a deliberate, narrow exception to this site's static-first default: progressive enhancement (see its `.js`-scoped CSS in `global.css`), `prefers-reduced-motion` support, and fine-pointer-only gating are all load-bearing, not optional polish. This isn't a green light for JS generally — don't add more of it elsewhere without the same rigor.
- Astro components: frontmatter (`---`) does data/props only, no business logic beyond simple mapping.
- Slugs are sanitized (`slugify()` inside the n8n workflow's "Build Article Entry" Code node, mirroring the same rules the old fetch script used) — don't assume a title-derived slug is already URL-safe without checking that node.

## Deployment

Netlify, connected to this repo. Build command `node scripts/generate-webp.mjs && astro build` (see "Hero/gallery image WebP optimization" below), output directory `dist` (see `netlify.toml`). No environment variables are required for the build itself. Every push to `main` — from n8n's automated commits or a manual commit — triggers a deploy; there is no manual "export" step.

**Netlify billing is credit-based, not build-minutes-based (confirmed 2026-09-03 against Netlify's own docs).** NOBS-team's plan gives 3,000 credits/month. A **production deploy costs a flat 15 credits regardless of build duration** (Deploy Previews/branch deploys are free) — build minutes aren't billed separately at all, so a slow build doesn't cost more, only a *separate* build does. The other real credit costs here: Netlify Functions compute at 10 credits/GB-hour (negligible for this repo's short admin/gallery/topics calls, and still cheap for `image-regen-run-background`'s longer runs), and — the one that scales with growth — **bandwidth at 20 credits/GB**, which is why the hero-image WebP optimization below exists.

**Batch commits — don't push one fix at a time.** Every push to `main` triggers a full production rebuild of all ~100+ pages (Astro isn't set up for incremental builds), each costing 15 credits flat as above. This bit hard on 2026-08-23: the 2026-08-21/22 link-fix and bug-fix sweeps pushed 98 and 181 commits on those two days respectively (one commit per individual fix), which meant ~279 separate full-site builds and burned 2.8K of the plan's 3,000 monthly credits in those two days alone — Netlify then paused all further production deploys ("running on operational credits") for the rest of the billing cycle, including two genuinely-ready commits that got silently skipped. No single build was expensive (~45s each); the volume of separate pushes was the entire cost. **When doing multi-fix work (a link sweep, a batch of article corrections, anything that touches many files across many small logical changes), batch related fixes into as few commits/pushes as reasonably traceable** — don't commit-and-push after every individual fix.

**Correction (2026-09-03): "Lock to stop auto publishing" does NOT save credits — it still builds every push, it just withholds publishing.** The line above used to recommend that lock for a multi-push work session; confirmed directly against Netlify's own docs that "stop auto publishing" keeps building on every push (and billing 15 credits each), it only holds the *result* back from going live. The lever that actually stops credit consumption is the separate, stronger **"Stop builds"** toggle on the Deploys page — that halts building entirely (0 credits for any push while it's active). Use "Stop builds" for a session where the goal is to avoid burning credits while iterating; do one manual "Trigger deploy" (15 credits) at the end. Reserve "stop auto publishing" for when you specifically want Netlify to keep validating each build without it going live yet (it doesn't save anything either way, it's a publish gate, not a cost control).

**`netlify.toml`'s `ignore` setting skips the build for `topics.json`-only commits (added 2026-08-26, rewritten 2026-09-03 after being confirmed broken in production).** Found the same credit-burning pattern recurring in a new form: n8n's topic-queue processing reports each topic's outcome via its own `Topics: update topic #N` commit to `src/data/topics.json` — observed firing roughly **every 20 minutes around the clock** (30 separate commits between 12:01 AM and 9:41 AM on 2026-08-26 alone), not "twice a day" as the 2026-08-21 reset entry below assumed (and not the "weekly schedule" the Known gaps section below also claims); both assumptions look stale and need re-confirming against the live n8n workflow's actual Schedule Trigger config. Auto-publish was left unlocked overnight, so each of those 30 commits triggered its own full rebuild *and* went live to production individually before the next replaced it. Root cause fixed at the source rather than relying on remembering to lock every night: `src/data/topics.json` is never imported by any Astro page (confirmed via `grep -r "topics.json" src/`) — it's only read/written at runtime by `netlify/functions/topics-*.js` via the GitHub API — so a commit touching only that file can never change the build output.

**Confirmed broken in production, 2026-09-03, by reading the real Deploys list:** the original one-line `git diff --quiet $CACHED_COMMIT_REF $COMMIT_REF -- . ':(exclude)src/data/topics.json'` had only ever been verified by replaying the diff *locally* against a full clone (see the paragraph below, kept for the record) — never against an actual Netlify build, despite that caveat being written down at the time. The real Deploys list for 2026-08-26 shows exactly why that mattered: a genuine topics-only commit (`7e8f764`, "Topics: update topic #9") built as a full `completed` production deploy 36 minutes after this rule first went live, instead of showing `Skipped` the way it should have. Best-guess root cause: `$CACHED_COMMIT_REF`'s commit object isn't guaranteed resolvable in Netlify's actual build checkout (a cold cache lineage, a cache eviction, etc.), and a `git diff` against an unresolvable ref errors out — an erroring `ignore` command exits non-zero, which Netlify safely defaults to "build normally," silently, with no distinguishing trace in the Deploys list between that and a real change being detected. **Fixed by replacing the one-liner with `scripts/should-ignore-build.sh`** (`ignore = "bash scripts/should-ignore-build.sh"`), which explicitly checks for a missing/unresolvable `$CACHED_COMMIT_REF` before attempting the diff (building rather than risking a false skip either way) and echoes what it's doing at each step, specifically so a future failure is diagnosable straight from the build log's "Initializing" phase instead of requiring the kind of after-the-fact Deploys-list forensics this one took.

**Verified working against a real live build, 2026-09-03** (commit `23b0ba3`, a genuine topics.json-only change with `a333407` as its `$CACHED_COMMIT_REF` baseline). The build log's "Initializing" phase showed the script's own `[ignore-check] only src/data/topics.json changed ... -- skipping build` line, followed by Netlify's own `User-specified ignore command returned exit code 0. Returning early from build.` — whole thing took 2.072s and never reached the Building/Deploying phases. **Important UI correction:** a successful ignore-skip does NOT show `Skipped` in the Deploys list — it shows as **"Deploy canceled" / "Your deploy failed due to an error"**, with the reason text `Canceled build due to no content change`. That alarming-looking label is the *correct*, intended outcome for an ignore-command skip, not a real failure — `Skipped` (no alarming wording) is a different mechanism entirely, used when a build gets superseded in the queue by a newer push before it starts (e.g. the `26b7f64` hero-image commit on 2026-08-26). Don't mistake one for the other when reading the Deploys list. Cost confirmation: credits dropped by ~15.2 across both this commit and the real build immediately before it (`a333407`) — consistent with exactly one real 15-credit deploy, not two.
